## 1. Prompt คือ "สเปกงาน" ไม่ใช่คาถา

หลายคนคิดว่า prompt engineering คือการหาคำพิเศษที่ทำให้ AI เก่งขึ้น
**จริงๆ แล้วมันคือการเขียนสเปกงานให้ชัด** เหมือนตอนที่คุณมอบงานให้พนักงานใหม่ที่เก่งมาก แต่ไม่รู้อะไรเกี่ยวกับบริษัทคุณเลย

ลองเทียบสองแบบนี้:

❌ **แบบคลุมเครือ**
```
สรุปยอดขายให้หน่อย
```

✅ **แบบสเปกชัด**
```
คุณกำลังช่วยเจ้าของร้านขายอุปกรณ์ไอทีเล็กๆ ที่ไม่มีพื้นฐานบัญชี
ข้อมูลยอดขายเดือนนี้อยู่ใน <sales> ด้านล่าง

งานของคุณ:
1. สรุปยอดขายรวม และเทียบกับเดือนก่อนเป็น %
2. บอกสินค้าขายดี 3 อันดับ
3. ชี้สิ่งผิดปกติที่เจ้าของควรรู้ (ถ้ามี)

ข้อกำหนด:
- ภาษาไทย ไม่เกิน 10 บรรทัด
- ห้ามคำนวณตัวเลขที่ไม่มีในข้อมูล ถ้าข้อมูลไม่พอให้บอกตรงๆ

<sales>
...
</sales>
```

### เช็กลิสต์ของ prompt ที่ดี
| หัวข้อ | คำถามที่ต้องตอบ |
|---|---|
| **บริบท** | ใครใช้ ใช้ทำอะไร ผู้อ่านเป็นใคร |
| **งาน** | ต้องทำอะไร ถ้ามีหลายขั้นให้เรียงเป็นข้อ |
| **ข้อมูล** | ข้อมูลอยู่ตรงไหน (แยกให้ชัดด้วย tag) |
| **รูปแบบผลลัพธ์** | ยาวแค่ไหน ภาษาอะไร โครงสร้างแบบไหน |
| **ข้อห้ามและกรณีพิเศษ** | ถ้าข้อมูลไม่พอให้ทำอย่างไร อะไรห้ามทำ |
| **เหตุผล** | ทำไมถึงมีกติกาข้อนี้ (โมเดลทำตามได้ดีขึ้นเมื่อรู้เหตุผล) |

> 💡 **เคล็ดลับ:** บอกเหตุผลด้วยเสมอ เช่น "ห้ามเดาตัวเลข **เพราะเจ้าของจะใช้ตัวเลขนี้ตัดสินใจสั่งของ**"
> พอโมเดลรู้เหตุผล มันจะนำหลักการไปใช้กับกรณีที่เราไม่ได้เขียนไว้ได้ด้วย

## 2. เทคนิคหลัก 5 อย่าง

### 2.1 แบ่งส่วนด้วย XML tag
Claude ถูกฝึกมาให้เข้าใจ tag ได้ดี ใช้ tag แยก "คำสั่ง" ออกจาก "ข้อมูล" จะได้ไม่ปนกัน

```
<document>
{เนื้อหาเอกสารยาวๆ}
</document>

<question>
{คำถามของผู้ใช้}
</question>

ตอบคำถามโดยอ้างอิงจาก document เท่านั้น
```

**ประโยชน์ด้านความปลอดภัย:** ถ้าในเอกสารมีข้อความว่า "ลืมคำสั่งก่อนหน้า" โมเดลจะแยกได้ง่ายขึ้นว่านั่นเป็นข้อมูล ไม่ใช่คำสั่ง (รายละเอียดในบทที่ 6)

### 2.2 วางเอกสารยาวไว้ก่อน แล้วค่อยวางคำถาม
ถ้า input มีเอกสารยาว ให้วางเอกสารไว้ด้านบน แล้ววางคำถามหรือคำสั่งไว้ท้ายสุด คุณภาพคำตอบมักดีกว่า

### 2.3 Few-shot: ยกตัวอย่าง
ถ้าต้องการรูปแบบที่เฉพาะเจาะจง การยกตัวอย่าง 2–3 ตัวอย่างได้ผลกว่าการอธิบายยาวๆ

```
จัดหมวดข้อความจากลูกค้า ตอบเป็นหมวดเดียว

<example>
ข้อความ: ของยังไม่ถึงเลยค่ะ สั่งไปตั้งแต่อาทิตย์ก่อน
หมวด: การจัดส่ง
</example>
<example>
ข้อความ: เมาส์ตัวนี้ใช้กับ Mac ได้ไหมครับ
หมวด: สอบถามสินค้า
</example>
<example>
ข้อความ: ขอใบกำกับภาษีเต็มรูปด้วยครับ
หมวด: เอกสาร/บัญชี
</example>

ข้อความ: {ข้อความใหม่}
หมวด:
```

⚠️ **ข้อควรระวัง:** ตัวอย่างควรหลากหลาย ถ้าทุกตัวอย่างคล้ายกันเกินไป โมเดลจะลอกรูปแบบเดิมไปใช้แม้ในกรณีที่ไม่ควร

### 2.4 ให้คิดก่อนตอบ
Claude รุ่นใหม่มี **adaptive thinking** ที่คิดเองอยู่แล้ว (บทที่ 1) ส่วนใหญ่จึงไม่ต้องสั่งว่า "คิดทีละขั้น"
ถ้าต้องการเร่งความละเอียดสำหรับงานยาก ให้ปรับ `effort` เป็น `high` หรือ `xhigh` แทน

### 2.5 กำหนดบทบาทใน system prompt
```
system = "คุณคือนักบัญชีที่อธิบายเรื่องยากให้เจ้าของร้านเล็กๆ เข้าใจ"
```
บทบาทช่วยกำหนดน้ำเสียงและระดับภาษา แต่ **ต้องเขียนงานให้ชัดด้วยเสมอ** บทบาทอย่างเดียวไม่พอ

## 3. Anti-patterns ที่ควรเลี่ยง

| ❌ อย่าทำ | ✅ ทำแทน |
|---|---|
| ตัวพิมพ์ใหญ่และคำขู่ เช่น "สำคัญมาก!!! ห้ามเด็ดขาด!!!" | เขียนกติกาธรรมดา พร้อมเหตุผล |
| บอกแต่สิ่งที่ห้ามทำ | บอกว่าควรทำอะไร เช่น "ตอบเป็นย่อหน้า" แทน "อย่าใช้ bullet" |
| prompt ยาวที่มีกติกาขัดกันเอง | อ่านทวนเหมือนคนอ่าน แล้วตัดส่วนที่ขัดกันออก |
| สั่งให้ตอบ JSON ด้วยข้อความแล้วหวังว่าจะได้จริง | ใช้ structured output (หัวข้อที่ 4) |
| แก้ prompt ตามความรู้สึก | ทำชุดทดสอบ (หัวข้อที่ 5) |

## 4. Structured Output — ให้ตอบเป็น JSON ที่เชื่อถือได้

ในงานจริง ผลลัพธ์ของ LLM มักต้องส่งต่อให้โค้ด เช่น บันทึกลงฐานข้อมูล หรือส่งเข้า ERPNext
ถ้าได้ข้อความอิสระกลับมา โค้ดจะอ่านยาก และพังได้ง่าย

**วิธีที่ถูกต้อง** คือส่ง `output_config.format` พร้อม JSON Schema ไปกับ request
API จะ **รับประกัน** ว่าคำตอบเป็น JSON ที่ตรง schema

```python
import json
from common import create, text_of

schema = {
    "type": "object",
    "properties": {
        "customer_name": {"type": "string"},
        "items": {
            "type": "array",
            "items": {
                "type": "object",
                "properties": {
                    "product": {"type": "string"},
                    "qty": {"type": "integer"},
                },
                "required": ["product", "qty"],
                "additionalProperties": False,
            },
        },
        "urgent": {"type": "boolean"},
    },
    "required": ["customer_name", "items", "urgent"],
    "additionalProperties": False,
}

email = """เรียนฝ่ายขาย
บริษัท สมใจการช่าง ต้องการสั่ง เมาส์ไร้สาย 10 ตัว และคีย์บอร์ด 5 ชุด
ขอด่วนภายในวันศุกร์นี้นะครับ  -- คุณสมชาย"""

response = create(
    max_tokens=16000,
    messages=[{
        "role": "user",
        "content": f"ดึงข้อมูลใบสั่งซื้อจากอีเมลนี้\n<email>\n{email}\n</email>",
    }],
    output_config={"format": {"type": "json_schema", "schema": schema}},
)

order = json.loads(text_of(response))
print(order["customer_name"])        # บริษัท สมใจการช่าง
for it in order["items"]:
    print(it["product"], it["qty"])
```

### ใช้ Pydantic เพื่อตรวจข้อมูลอีกชั้น
Pydantic เป็นไลบรารีมาตรฐานของ Python สำหรับกำหนดและตรวจโครงสร้างข้อมูล (FastAPI ในบทที่ 11 ก็ใช้ Pydantic)

```python
from pydantic import BaseModel, Field

class OrderItem(BaseModel):
    product: str
    qty: int = Field(gt=0)          # ต้องมากกว่า 0

class Order(BaseModel):
    customer_name: str
    items: list[OrderItem]
    urgent: bool

order = Order.model_validate_json(text_of(response))
print(order.items[0].qty)
```

> Schema รับประกันแค่ **รูปแบบ** ไม่ได้รับประกันว่า **ค่าถูกต้อง**
> Pydantic ช่วยตรวจกติกาทางธุรกิจเพิ่มได้ เช่น จำนวนต้องมากกว่า 0
> **ข้อมูลจาก LLM ต้องผ่านการตรวจก่อนนำไปเขียนลงระบบจริงเสมอ**

### ข้อจำกัดของ schema ที่ควรรู้
- ทุก object ควรมี `"additionalProperties": False` และ `required`
- ถ้าฟิลด์ไหนอาจไม่มีข้อมูล ให้ใช้ `{"type": ["string", "null"]}` แล้วใส่ใน `required` ไว้ อย่าเว้นฟิลด์ไว้เฉยๆ

## 5. ทดสอบ Prompt อย่างวิศวกร

การแก้ prompt แล้วลองถามคำถามเดียว แล้วรู้สึกว่าดีขึ้น **ไม่ใช่การทดสอบ**
ให้สร้าง **ชุดทดสอบเล็กๆ** ตั้งแต่ต้น

```python
TEST_CASES = [
    {"email": "ขอเมาส์ 3 ตัว ด่วนมาก", "expect_urgent": True,  "expect_count": 1},
    {"email": "สนใจคีย์บอร์ด 2 ชุดกับจอ 1 จอ", "expect_urgent": False, "expect_count": 2},
    {"email": "สวัสดีครับ แค่สอบถามราคา", "expect_urgent": False, "expect_count": 0},
]

passed = 0
for case in TEST_CASES:
    order = extract_order(case["email"])       # ฟังก์ชันที่ห่อโค้ดข้างบน
    ok = (order.urgent == case["expect_urgent"]
          and len(order.items) == case["expect_count"])
    passed += ok
    print("✅" if ok else "❌", case["email"])

print(f"ผ่าน {passed}/{len(TEST_CASES)}")
```

ทุกครั้งที่แก้ prompt ให้รันชุดนี้ใหม่ ถ้าคะแนนลดลงแปลว่าแก้แล้วพัง
แนวคิดนี้คือ **evals** ซึ่งเป็นทักษะที่บริษัทต้องการมาก บทที่ 12 จะลงลึกเรื่องนี้

## 6. Prompt Caching — ประหยัดเงินเมื่อ prompt ยาว

ถ้า system prompt ยาว (เช่น คู่มือบริษัท 20 หน้า) และส่งซ้ำทุกครั้ง จะเสียเงินซ้ำทุกครั้ง
**Prompt caching** ให้ API จำส่วนต้นของ prompt ไว้ครั้งต่อไปที่ส่งส่วนเดิมซ้ำ จะคิดราคาส่วนนั้นถูกลงมาก

```python
response = create(
    max_tokens=16000,
    cache_control={"type": "ephemeral"},   # เปิด caching อัตโนมัติ
    system=LONG_COMPANY_MANUAL,            # ส่วนที่ไม่เปลี่ยน วางไว้ก่อน
    messages=[{"role": "user", "content": question}],   # ส่วนที่เปลี่ยน วางไว้หลัง
)
print(response.usage.cache_read_input_tokens)   # มากกว่า 0 แปลว่า cache ถูกใช้
```

**กฎสำคัญ:** cache ทำงานแบบ **prefix match** คือต้องตรงกันตั้งแต่ตัวอักษรแรก
- ❌ อย่าใส่ข้อมูลที่เปลี่ยนทุกครั้ง เช่น วันที่หรือเวลาปัจจุบัน ไว้ต้น system prompt เพราะ cache จะพลาดทุกครั้ง
- ✅ วางส่วนที่คงที่ไว้ก่อน ส่วนที่เปลี่ยนไว้ท้าย
- prompt ที่สั้นเกินไปจะไม่ถูก cache (ขั้นต่ำประมาณหลักพัน token ขึ้นกับรุ่นโมเดล)

## สรุปบทที่ 2
1. Prompt คือสเปกงาน ให้เขียนบริบท งาน ข้อมูล รูปแบบ ข้อห้าม และเหตุผลให้ครบ
2. ใช้ XML tag แยกคำสั่งออกจากข้อมูล และใช้ few-shot เมื่อต้องการรูปแบบเฉพาะ
3. ใช้ `output_config.format` ให้ได้ JSON ที่ตรง schema แล้วตรวจซ้ำด้วย Pydantic
4. ทดสอบ prompt ด้วยชุดทดสอบ ไม่ใช่ด้วยความรู้สึก
5. Prompt caching ช่วยประหยัดเงินได้มาก ถ้าวางส่วนที่คงที่ไว้ก่อน

## 1. จาก Tool Use สู่ Agent

บทที่ 3 เรียกเครื่องมือแค่ **รอบเดียว** แต่งานจริงมักต้องทำหลายขั้น เช่น:

> "ดูว่ามีไฟล์รายงานอะไรบ้าง อ่านทุกไฟล์ แล้วเขียนสรุปรวม"

ขั้นตอนของงานนี้คือ list → read → read → read → write ซึ่งเราไม่รู้ล่วงหน้าว่าต้องกี่รอบ
**agent จึงให้โมเดลเป็นคนตัดสินใจว่าจะทำอะไรต่อ จนกว่าจะเสร็จ**

```python
while True:
    response = llm(messages, tools)
    if response.stop_reason == "end_turn":   # โมเดลบอกว่าเสร็จแล้ว
        break
    results = run_tools(response)            # รันเครื่องมือที่ขอ
    messages += [response, results]          # ป้อนผลกลับเข้าไป
```

นี่คือวงจร **Observe → Think → Act** (ReAct) ที่คุยกันไว้ตั้งแต่ต้น

## 2. Workflow หรือ Agent?

ก่อนสร้าง agent ให้ถามตัวเองก่อน เพราะ agent **แพงกว่า ช้ากว่า และคาดเดายากกว่า**

| แบบ | ใครเป็นคนกำหนดขั้นตอน | เหมาะกับ |
|---|---|---|
| **เรียก LLM ครั้งเดียว** | — | จัดหมวด, สรุป, ดึงข้อมูล |
| **Workflow** | โค้ดของเรา (A → B → C ตายตัว) | ขั้นตอนที่รู้ล่วงหน้า เช่น อีเมล → ดึงใบสั่งซื้อ → ตรวจ → บันทึก |
| **Agent** | โมเดล | งานที่ขั้นตอนเปลี่ยนตามสถานการณ์ เช่น "หาสาเหตุที่ยอดขายตก" |

**เช็คลิสต์ก่อนใช้ agent:**
1. งานซับซ้อนจนกำหนดขั้นตอนล่วงหน้าไม่ได้ใช่ไหม
2. ผลลัพธ์คุ้มกับค่าใช้จ่ายและเวลาที่เพิ่มขึ้นไหม
3. โมเดลทำงานประเภทนี้ได้ดีไหม
4. ถ้าทำผิด ตรวจเจอและแก้คืนได้ไหม

ถ้ามีข้อไหนตอบว่า "ไม่" ให้ใช้ workflow แทน

### Workflow patterns ที่ใช้บ่อย
| Pattern | คำอธิบาย | ตัวอย่าง |
|---|---|---|
| **Prompt chaining** | ผลลัพธ์ของ LLM ตัวแรก → เป็น input ของตัวถัดไป | ร่างอีเมล → ตรวจน้ำเสียง → แปล |
| **Routing** | จัดหมวดก่อน แล้วส่งต่อให้ prompt เฉพาะทาง | คำถามบัญชี → prompt บัญชี / คำถามสต็อก → prompt คลัง |
| **Parallelization** | แบ่งงานย่อยให้ LLM ทำพร้อมกัน | สรุปรายงาน 10 สาขาพร้อมกัน แล้วรวมผล |
| **Evaluator–optimizer** | ตัวหนึ่งสร้าง อีกตัวตรวจ แล้ววนแก้ | เขียน SQL → ตรวจ → แก้ |

## 3. Mini Agent ฉบับเต็ม

โค้ดเต็มอยู่ที่ [lab/mini_agent.py](lab/mini_agent.py) (ต้องคัดลอก `common.py` จากบทที่ 1 มาไว้ด้วย)

### โครงสร้าง
```
mini_agent.py
├── TOOLS           นิยามเครื่องมือ: list_files / read_file / write_file
├── safe_path()     🔒 กันไม่ให้ออกนอก workspace
├── HANDLERS        map ชื่อเครื่องมือ → ฟังก์ชัน Python
├── run_tool()      รันเครื่องมือ และจับ error
├── log()           บันทึกทุก step ลง agent_log.jsonl
└── run_agent()     ลูปหลัก + จำกัดจำนวนรอบ
```

### ส่วนที่ 1: ลูปหลัก
```python
def run_agent(goal: str) -> str:
    messages = [{"role": "user", "content": goal}]

    for turn in range(1, MAX_TURNS + 1):              # ① จำกัดจำนวนรอบ
        response = create(max_tokens=16000, system=SYSTEM,
                          tools=TOOLS, messages=messages)
        messages.append({"role": "assistant", "content": response.content})

        if response.stop_reason == "end_turn":         # ② จบปกติ
            return text_of(response)
        if response.stop_reason != "tool_use":         # ③ หยุดแบบอื่น
            return f"หยุด: {response.stop_reason}"

        results = [run_tool(b) for b in response.content if b.type == "tool_use"]
        messages.append({"role": "user", "content": results})   # ④ ป้อนผลกลับ

    return "หยุด: ครบจำนวนรอบสูงสุดแล้ว"
```

**① MAX_TURNS** คือเบรกฉุกเฉิน ถ้าโมเดลวนทำซ้ำไม่จบ ค่าใช้จ่ายจะพุ่งขึ้นเรื่อยๆ
ถ้าไม่มีตัวนี้ บิลอาจบานได้ในคืนเดียว

**② ③ เช็ค stop_reason ทุกกรณี** อย่าเขียนว่า "ถ้าไม่ใช่ end_turn ก็ถือว่าเป็น tool_use" เพราะอาจเป็น `max_tokens` หรือ `refusal` ก็ได้

**④ ผลของเครื่องมือทุกตัวต้องอยู่ใน user message เดียว**

### ส่วนที่ 2: Sandbox ของ path
```python
def safe_path(rel: str) -> Path:
    p = (WORKSPACE / rel).resolve()
    if not p.is_relative_to(WORKSPACE):
        raise PermissionError(f"ไม่อนุญาตให้เข้าถึงนอก workspace: {rel}")
    return p
```
ถ้าไม่มีฟังก์ชันนี้ โมเดลอาจถูกหลอกหรือเข้าใจผิด แล้วเขียนไฟล์ไปที่ `../../` ได้
**อย่าเชื่อ input จากโมเดล** ให้ปฏิบัติเหมือนเป็น input จากผู้ใช้ที่ต้องตรวจทุกครั้ง

### ส่วนที่ 3: ตัดผลลัพธ์ที่ยาวเกินไป
```python
if len(text) > 20_000:
    return text[:20_000] + f"\n...[ตัดทอน: ไฟล์ยาว {len(text)} ตัวอักษร]"
```
ถ้าไฟล์ยาว 1 ล้านตัวอักษรเข้าไปใน context จะเปลืองเงินและทำให้โมเดลสับสน
**ต้องบอกโมเดลด้วยว่ามีการตัด** มันจะได้รู้ว่ายังเห็นข้อมูลไม่ครบ

### ส่วนที่ 4: Log
ทุก step ถูกบันทึกลง `agent_log.jsonl` (1 บรรทัดต่อ 1 เหตุการณ์)
เวลา agent ทำอะไรแปลกๆ log คือเครื่องมือเดียวที่ช่วยให้รู้ว่าเกิดอะไรขึ้น (observability ในบทที่ 12)

## 5. Failure modes ที่จะเจอ

| อาการ | สาเหตุ | วิธีแก้ |
|---|---|---|
| วนเรียกเครื่องมือเดิมซ้ำๆ | ผลลัพธ์ไม่ชัด หรือ error message ไม่ช่วยให้แก้ต่อได้ | ปรับ error message และจำกัดจำนวนรอบ |
| ตอบว่าเสร็จแล้ว แต่ยังไม่ได้ทำ | ไม่มีขั้นตรวจสอบ | ให้ตรวจผลลัพธ์ก่อนจบ (เช่น อ่านไฟล์ที่เพิ่งเขียน) หรือให้โค้ดตรวจเอง |
| ใช้เครื่องมือผิดตัว | description ไม่ชัดหรือทับซ้อนกัน | เขียน description ใหม่ |
| ค่าใช้จ่ายสูง | context โตขึ้นทุกรอบ | บทที่ 5: context management |
| ทำเกินกว่าที่สั่ง | ขอบเขตงานไม่ชัด | ระบุขอบเขตใน system prompt และจำกัดสิทธิ์ของเครื่องมือ |

## 6. เทียบกับ Framework

| ตัวเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| **เขียนเอง** (บทนี้) | เข้าใจทุกบรรทัด ควบคุมได้ 100% | ต้องเขียนเองทุกอย่าง |
| **SDK tool runner** | สั้น เป็นทางการ มี hook ให้แทรกโค้ด | เป็น beta |
| **Claude Agent SDK** | ได้ harness ของ Claude Code ทั้งชุด (อ่าน/เขียนไฟล์, bash, subagent) | ใหญ่ ใช้กับงานทั่วไปที่ไม่ใช่งานไฟล์ได้ยากกว่า |
| **LangGraph / LlamaIndex / CrewAI** | มีตัวอย่างและ ecosystem เยอะ พบบ่อยใน job description | มีชั้น abstraction หลายชั้น debug ยาก |
| **Managed Agents (Anthropic)** | Anthropic รันลูปและ sandbox ให้ ไม่ต้องดูแลเซิร์ฟเวอร์ | ต้องพึ่งแพลตฟอร์ม |

> 🎓 **ในการสัมภาษณ์:** ถ้าอธิบายได้ว่า framework ทำอะไรอยู่เบื้องหลัง (ซึ่งก็คือลูปในบทนี้) จะได้เปรียบคนที่ใช้เป็นแค่ library มาก

## สรุปบทที่ 4
1. Agent = LLM + เครื่องมือ + ลูป ที่โมเดลเป็นคนตัดสินใจขั้นต่อไป
2. เลือก workflow ก่อน ถ้าขั้นตอนรู้ล่วงหน้า
3. ต้องมีเสมอ: จำกัดจำนวนรอบ, ตรวจ stop_reason ทุกกรณี, sandbox, ตัดผลลัพธ์ยาว, log
4. อย่าเชื่อ input ที่มาจากโมเดล ให้ตรวจเหมือน input จากผู้ใช้

## แบบฝึกหัด
1. เพิ่มเครื่องมือ `search_in_files(keyword)` ที่คืนชื่อไฟล์และบรรทัดที่พบคำนั้น
2. เพิ่ม **งบประมาณ**: ให้ agent หยุดเมื่อใช้เงินเกิน $0.20 (ใช้ `cost_usd` จาก common.py)
3. เพิ่ม **ตัวตรวจจับการวนซ้ำ**: ถ้าเรียกเครื่องมือเดิมด้วย input เดิม 3 ครั้ง ให้ส่ง error บอกโมเดลว่ากำลังทำซ้ำ
4. เขียน agent เดียวกันใหม่ด้วย **tool runner** (บทที่ 3 หัวข้อ 9) แล้วเทียบจำนวนบรรทัด
5. **Capstone:** เปลี่ยนเครื่องมือไฟล์เป็นเครื่องมือจำลองของร้าน (`get_stock`, `get_sales`) แล้วถามว่า "สินค้าไหนควรสั่งเพิ่ม"
